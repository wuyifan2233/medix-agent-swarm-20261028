## 数据库到底怎么统一

只有一份 SQLite **业务数据库**：默认 `.medix-data/app.db`，由 Alembic 自动升级到单一 head `20261031_17`。包含账号、档案、偏好、病例、记忆、本地提醒、送达、渠道绑定。导入模块复用 `storage/business.py`，不再读取各成员的病例/提醒 SQLite 文件。

- `MEDIX_DATABASE_URL` / `MEDIX_DATA_DIR`：业务数据。
- `MEDIX_DB_PATH` / `--db-path`：公共医学资料的向量索引，独立目录，不能指向业务 SQLite 文件。
- `MEM0_API_KEY`：可选云端长期记忆服务。命名空间包含环境、账号和人物。
- 同学的本机数据库不会被 Git 带过来，也不会自动搬入。新环境第一次启动是空账号库；测试数据或需要保留的资料应另做明确迁移。
- 本地用户外键关联数据随注销清理；远程 Mem0 的物理清除不作为已完成项目，新注册 UUID 不会再访问旧账号记忆。

## 微信/QQ接入边界

这是消息渠道，不是用微信或 QQ 登录网页。先登录 MediX 手机号账号，连接结果绑定其 `user.id`，不需要再给机器人独立绑定手机号。

- 本地桥接每个渠道只有一个物理连接账号；不是无限人数同时扫码的公共机器人平台。其他 MediX 账号不能接管已有连接。
- 微信仅接收扫码确认身份的私聊消息；QQ好友需回复一次性绑定码，确认前不开放医疗问答与推送。
- QQ依赖本机 QQ 与 SnowLuma/OneBot 环境；微信依赖该分支使用的 iLink 接口。是否可用仍受客户端、网络和平台限制。
- 停用账号不再产生新提醒或发送已排队的渠道内容。重启恢复提醒数据；渠道凭证保留，但需在页面点击连接后启动桥接，避免未确认就对外发消息。

## 证据模式的全局路由修复

原知识库query_policy负责医学检索内部规则；web/app.py曾在Swarm之前对所有请求执行覆盖检查，误拦截身份、记忆、提醒及闲聊。现在配置模型的证据模式先由web/request_routing.py依据问题和当前账号内近期上下文语义分流：medical（医学咨询）、report（报告）、personal（身份/记忆）、action（提醒/管理操作）、conversation（普通对话）。已有Swarm保留后续Agent与工具分工，不承担绕过账号权限的职责。

只有medical的证据覆盖不足会提前返回；report可以读取用户给出的事实，不能据缺失证据扩展诊疗结论。personal/action/conversation不查询公共医学知识库、不抽取病例，记忆查询继续使用服务端user.id及本人/父母分组。个人身份只能引用账号展示名和已提供资料，不把昵称当实名。分类失败提示请求路由未完成，不伪装成医学资料不足。无模型配置时保持原有离线医学检索；纯问候的本地快捷回复只是优化，不是总体意图路由。

语义分类为单独模型调用，计入同一轮Token与关怀点；流式只展示正式正文，不展示分类JSON。医学direct路径的单次调用仅指正文生成。

验证：Windows/Python3.10整套363项离线回归通过。浏览器真实验证「我是谁」按当前账号昵称与可用记忆回答、「什么是高血压」继续医学检索并返回引用；报告缺公共覆盖不拦截转录、提醒/闲聊不查询公共库、双账号记忆归属由新增测试覆盖。没有把模拟提醒或报告测试称为真实渠道/图片服务验收。
